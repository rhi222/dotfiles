# Slackのスタンプから Linear へ起票する

Slack上で「これタスクだ」と気づいた瞬間にスタンプを押すだけで、Linear の Triage に
ポインタが積まれるようにする。判断（要約とタイトル生成）だけをここで行い、
状態変更（重複チェック・起票・処理済み記録）は `scripts/linear/slack-sweep.sh` に任せる。
スクリプトは `$(ghq root)/github.com/rhi222/dotfiles/scripts/linear/slack-sweep.sh` で解決する
（どのリポジトリで作業中でも呼べるように、cwd 相対では書かない）。

**Slackへは一切書き込まない。** リンクは Linear → Slack の一方向のみ。
Slackはチームの共有物なので、個人のタスク管理都合のノイズを持ち込まない。
Slackへ書き込めるツールはこのskillに許可されていない（Slack側は読み取り系MCPのみ）。

## 設定

| 変数 | 既定値 | 意味 |
| --- | --- | --- |
| `LINEAR_SLACK_EMOJI` | `nishiyama_todo` | 起票トリガのスタンプ名 |
| `LINEAR_SLACK_SWEEP_MAX` | `20` | 1回で処理する上限（`unseen` が担保する） |

## 手順

### 1. 候補を検索する

`mcp__claude_ai_Slack__slack_search_public_and_private` を呼ぶ。

- `query`: `hasmy::<EMOJI>:`
- `sort`: `timestamp`
- `include_context`: `false`
- `limit`: `20`

結果が20件なら `cursor` で次ページも取る。**全ページ取り切る。**

**日付で絞らない。** `after:` が絞るのは**メッセージの投稿日**であって、スタンプを押した日ではない。
遡り日数を置くと、古いスレを掘り返してスタンプを押したものが窓の外に落ちて永久に拾われなくなる。
過去スレのタスク化はふつうに起きるので、この取りこぼしは許容できない。

**窓を持たない代わりに、処理済み記録が冪等性を担保する。** 何度スキャンしても二重起票にならず、
cronが落ちた日があっても次回が勝手に拾い直す。

**ヒット数はスタンプを押すたびに単調増加する**（起票してもSlack側のリアクションは残るため）。
今は全期間で数件なので1ページで収まる。ページングが常時数ページに達するようになったら、
そのとき窓の再導入を検討する。

ヒット0件ならここで終了し、`起票対象なし` とだけ報告する。

### 2. 処理済みを落とす

各ヒットから `<channel_id>/<message_ts>` の形のキーを作る（検索結果の `Channel: ... (ID: Cxxx)`
と `Message_ts:` から組む）。まとめてスクリプトに渡し、残ったものだけを次へ進める。

```bash
bash "$(ghq root)/github.com/rhi222/dotfiles/scripts/linear/slack-sweep.sh" unseen \
  "C123/1786335015.733309" "C456/1786111487.003049"
```

**スレを読む前にここで絞る。** 読解コストが一番高いので、関門を手前に置く。
出力が空なら `新規なし` と報告して終了する。

### 3. スレを読む

残ったキーごとに `mcp__claude_ai_Slack__slack_read_thread` を呼ぶ。

- `channel_id`: キーの前半
- `message_ts`: 検索結果のpermalinkに `thread_ts=` があればその値、無ければキーの後半
- `response_format`: `detailed`（`Reactions:` を得るため）

出力から **`Message TS:` がキーの後半と一致するもの**を対象メッセージとして特定する。

**見つからないときに「リアクション不在」と断じない。** 返信が既定の取得件数（100件）を超える
スレでは、対象が後方にいて出力に入らないことがある。その場合は `oldest` にキーの ts の
**整数部から1を引いて `.000000` を付けた値**を渡して読み直す（`oldest` は排他的なので、
ts ちょうどを渡すと対象自身が落ちる）。

それでも対象が出てこなければ**判定不能**として扱い、処理済みにせず報告に出す。
不在と混同すると、毎回スキップされ続けて永久に起票されないまま誰も気づかない。

対象を特定できたら**2つのことをする**。

1. **リアクションの実在を確認する。** 対象メッセージの `Reactions:` に `<EMOJI>` が
   居なければ**スキップする**（起票しない）。Slack検索は絵文字名が実在の英単語のとき
   本文にもフォールバックするため、これが誤検知の最終防壁になる。
   スキップしたキーは処理済みにせず、次回また評価させる
2. **スレ全体を文脈として読む**

### 4. 起票する

スレから3つを作る。

| 項目 | 作り方 |
| --- | --- |
| タイトル | 「何をするのか」が動詞で分かる1行。Slackの発言をそのまま切らない |
| 期待アウトカム | 「何ができたら終わりか」の1行 |
| 経緯 | スレの要約。3行以内 |

**prefixは付けない。** `draft仕上げ:` はdraft PRが実在するもの、`実装:` はPRがまだ無い工程に
使う語で、Slack起点のものはどちらでもない。工程の分類は朝のtriageで人間が決める。

あわせて `role:*` と `em:*` を**各軸1つずつ推定する**。判定基準は起票規約と同じ2軸で、
Projectや親子付けと違って**スレを読めば決まる**。

| 軸 | 値 | 判定 |
| --- | --- | --- |
| role | `role:player` | 自分が手を動かす |
| role | `role:manager` | 人を動かす・決める |
| em | `em:people` | 人・採用・育成・評価・体制 |
| em | `em:tech` | 技術方針・設計・実装・基盤・品質 |
| em | `em:project` | 進行・段取り・リスク・調整 |
| em | `em:product` | 何を作るか・仕様・ドメイン・価値 |

**迷っても「付けない」を選ばない。** 未ラベルは週次のクロス集計で `role:?` / `em:?` の
1マスに集まり、配分が読めなくなる。**推定が暫定であることは state = `Triage` が表している**ので、
外れていれば朝のtriageで直せばよい。実際、朝のtriageに委ねていた10件が全て未分類のまま残った。

- **判断材料はここが一番多い。** スレ全文を読んだ直後のこの時点が、朝のtriageで人間が
  タイトルだけを見るより情報量が多い。読解コストは手順3で払い済みなので追加コストもほぼ無い
- draft PRスイープが `role:player` + `em:tech` を起票時に確定させているのと同じ扱い

キーごとに1回呼ぶ。

```bash
bash "$(ghq root)/github.com/rhi222/dotfiles/scripts/linear/slack-sweep.sh" create \
  "<key>" "<permalink>" "<タイトル>" "<期待アウトカム>" "<経緯>" \
  "role:player" "em:tech"
```

`src:slack` はスクリプトが固定で付けるので渡さない。許可されていないラベル名は無視され、
起票そのものは成功する（警告がstderrに出る）。

スクリプトが返すのは次のいずれか。

| 出力 | 意味 |
| --- | --- |
| `created NSY-xxx` | 新規に起票した |
| `commented NSY-xxx` | 同じスレのissueが既にあったのでコメントを足した |
| `skipped(seen) <key>` | 既に処理済みだった |

### 5. 報告する

起票した件数と、`NSY-xxx / タイトル / 推定したラベル` の一覧を出す。
**推定ラベルを出すのは、間違っていたときに人間がその場で気づけるようにするため。**
スキップしたものがあれば**理由ごとに**件数を添える（リアクション不在 / 判定不能）。

**判定不能はキーも出す。** 件数だけだと毎回同じものが落ち続けていても気づけない。

## やらないこと

- **Slackへの書き込み**（返信・スタンプ・canvas）
- **Project の選択と親子付け。** ここは朝のtriageで人間が決める。どちらもスレの外（既存の
  課題体系のどこに属すか）を知らないと決まらないので、スレを読んだだけでは判断材料が足りない。
  `role:*` / `em:*` を推定するのとはこの点が違う
- **既存issueが見つかったとき（`commented`）のラベル付け直し。** 既にtriageを通って人間が
  付け直しているかもしれないので、スレを読み直しただけの機械が上書きしない
- **Triage以外のstateへの起票。** Triageは「人間が選別する受信箱」なので、そこを迂回しない
