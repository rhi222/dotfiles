# doc-refine: 文書推敲パイプライン

ファイルを受け取り、4フェーズのパイプラインを全自動で回して元ファイルを修正するスキル。

## 使い方

```
/doc-refine <ファイルパス>
```

ファイルパスが省略された場合、ユーザーに確認する。

## 処理フロー

以下の4フェーズを**中断なく**順番に実行する。途中でユーザーに確認を求めない。

### Phase 1: 論理批評

`references/logic-patterns.md` のパターンに基づき、文章の論理的な問題を検出する。

1. 対象ファイルを Read で読み込む
2. 以下の観点で問題箇所を特定する:
   - **L1 因果の飛躍**: A→Bの間に暗黙の前提がないか
   - **L2 接続の断絶**: 前後の文の論理的つながりが不明でないか
   - **L3 根拠なき断定**: 「〜が必要」「〜すべき」に理由があるか
   - **L4 スコープの飛躍**: 個別→一般の急な飛躍がないか
   - **L5 暗黙の前提**: 読者が知らない前提に依存していないか
3. 各問題に ID (L1, L2, ...) と行番号を振る
4. 検出結果を内部的に保持する（まだ修正しない）

### Phase 2: AIくささ検出

`~/.claude/skills/humanize/references/ja-patterns.md` および `~/.claude/skills/humanize/SKILL.md` のパターンに基づき、AI特有の表現を検出する。

1. humanize スキルの Pass 1（パターン検出）と同じ処理を行う:
   - **A系**: コンテンツ系（誇張、曖昧な出典、定型的結論、マーケティング調）
   - **B系**: 言語系（AI頻出語彙、copula回避、ing付け足し、3要素列挙、過剰ヘッジング）
   - **C系**: スタイル系（ダッシュ過用、太字過用、箇条書き依存、絵文字過用）
   - **D系**: コミュニケーション系（チャットボット残留、追従的トーン、学習データ免責）
2. 各問題に既存 ID (A1, B2, ...) と行番号を振る
3. 検出結果を内部的に保持する（まだ修正しない）

### Phase 3: 修正実施

Phase 1 + 2 の検出結果を統合し、修正を実施する。

1. 検出結果を深刻度で並べ替える:
   - 論理の飛躍（L1〜L5）は意味に直結するため優先度高
   - AIくささ（A〜D系）は表現の問題なので次に対処
2. 修正ルール:
   - **元の意味・主張を変えない**。表現と論理の補足のみ
   - 論理の問題（L系）: 省略されたステップや根拠を補足する。ただし元の主張を変えない
   - AIくささ（A〜D系）: humanize スキルの修正方針に従う
   - 「魂のある文章」への転換も意識する（意見を持つ、リズムを崩す、具体的に書く）
   - 文体の一貫性を保つ（です/ます調 と だ/である調 の混在を避ける）
3. Edit ツールで元ファイルを直接修正する
4. 修正内容をログとして記録する

### Phase 4: 整合性チェック

修正前後で意味が変わっていないか確認する。

1. 修正前の内容と修正後の内容を比較する
2. チェック観点:
   - 元の主張が維持されているか
   - 削除された情報がないか（表現の変更は許容、情報の欠落は不可）
   - 新たな主張が追加されていないか（論理の補足は許容、新たな主張は不可）
3. 問題を発見した場合は再修正する

### 出力

修正完了後、以下の形式で修正サマリーを表示する:

```
修正完了: <ファイルパス>

---
**修正サマリー** (N件)
- [ID] line XX: 修正内容の簡潔な説明
- [ID] line XX: 修正内容の簡潔な説明
...
```

## 注意事項

- **文脈判断**: ビジネスメールの敬語、Marpのフロントマター、コードブロック内は修正対象外
- **技術的正確性**: 修正によって技術的な正確性が損なわれないようにする
- **過剰修正の防止**: すべてのパターンを機械的に除去しない。文脈に応じて判断する
- **スライド特有の考慮**: ノート（`<!-- note -->` や Marp の `---` 区切り後）がある場合、本文とノートの整合性も確認する
- **ファイル形式**: Markdown、Marpスライド、プレーンテキストに対応
