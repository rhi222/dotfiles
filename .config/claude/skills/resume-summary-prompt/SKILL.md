# 職務経歴書の要約依頼文

下の「依頼文」をコードブロックのまま出力し、使い方を1行添えて終える。

使い方: Google DriveでGeminiを開き、職務経歴書を添付して依頼文を貼る。

## 守ること

- **職務経歴書の本文を読まない。** PDF、Google Drive（MCP含む）、貼り付けられた本文のいずれも開かない。
  読むとセッションログに個人情報が残り、日報やkb-harvestの入力として下流へ流れるため
- ユーザーが職務経歴書の本文やURLを渡してきた場合も、内容には触れずに依頼文だけを返す
- 出力形式の調整を頼まれたら、依頼文を直してから出力する。恒久的な変更ならこのファイルを直すよう提案する

## 依頼文

```
添付の職務経歴書を、採用面談前の事前把握用に要約してください。

# 出力形式
略歴
* 社会人になった年、正社員としての通算期間
* エンジニアになった年（社会人歴とは別に数える。エンジニア以外の職歴があれば職種と期間も書く）
* 会社名(雇用形態): 開始年月〜終了年月（期間）
  ※ 現職は「〜現在（約N年Nヶ月）」と書く。今日の日付を基準に計算する

技術スキル
* 主な経験言語: 経験期間の長い順に3つまで（例: Java 約10年 / PHP 約5年 / Go 約2年）
  ※ この行だけは下の対象技術に限らず、経歴書に出てくる全言語から選ぶ。期間は案件期間の合計で概算する
* 技術名: 使い始めた時期（「YYYY.MMごろから」）
  ※ 対象は次の技術だけ。それ以外は書かない
    Node.js / TypeScript / JavaScript / Next.js / React / NestJS / AWS（使ったリソース名を併記。例: AWS（Lambda, ECS, RDS）: 2021.04ごろから）
  ※ 経歴書で実務利用が確認できるものだけを書く。対象技術の経験が無ければ「該当なし」と書く

活躍できそうなポジション（推測おおめ）
* 判断を1行で書き、その下の行に、経歴書のどの記述をもとにしたかを書く
* 観点: 顧客折衝・要件定義の経験 / 設計と実装の比率 / リーダーとプレイヤーのどちらに近いか

面談で確認したい点
* 経歴書だけでは判断できず、面談で聞くべきことを3つまで

所感
* 1〜2行

# ルール
* 経歴書に書いてある事実と推測を区別する。推測には「（推測）」と付ける
* 書いていないことは「記載なし」とし、補わない
* 年齢・性別・国籍・家族構成など、職務と関係のない属性を評価に使わない
* 期間の計算に自信がないときは、元の記載をそのまま併記する
```
