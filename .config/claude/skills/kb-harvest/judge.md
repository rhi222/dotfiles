# kb-harvest 判定基準（subagent向け）

渡されたdigestファイルを読み、ナレッジベースに残す候補を抽出する。
vaultは読まない。書き込みもしない。候補をJSONで返すだけにする。

digestが長いときは Read の offset / limit で分けて全部読む。

## KBに入れる条件（すべて満たす）

1. 他の人や他リポジトリのAIが読んでも価値がある
2. session中に確定した事実である。コード、ドキュメント、ユーザーの発言で裏付けがある
   - AIの推測のまま確定しなかったものは `confidence: "low"` で返す
3. コードを読めばすぐ分かることではない
4. 次の「拾う対象」のどれかに当てはまる

## 拾う対象

1. **用語（`term`）を最優先で拾う。**
   システム、サブシステム、バッチ、IF、画面、顧客やprojectの略号、組織単位（部・セクション・グループ・チーム）や職種・役割の名前、社内の呼び名の意味がsession中に確定したら、単独の `term` として出す
   - 意味を定める発言・ドキュメント・コードがsession中にある用語だけを出す。名前が出てきただけで、意味を文脈から推し量るしかない用語は出さない
   - 他の候補の本文に出てくる用語でも、別に `term` として出す。1 sessionに複数あれば全部出す
   - 同じものをシステムやチームで別の名前で呼んでいると分かったら、`別名:` に書く
2. **リポジトリをまたぐ知識（`system`、`scope: "cross-repo"`）。**
   あるIFをどのサブが使っているか、ある機能がどのサブの実装に分かれているか、サブ間のデータの流れ
3. **project固有の知識（`system`、`scope: "project"`）。**
   顧客ごとのprojectについて、そのシステム構成、どのサブとどのサブが連携しているか、そのprojectだけの例外
4. **組織の構造と決めごと（`org`）。**
   - 組織単位の担当範囲と、上下関係（どの組織の下にあるか）、組織単位どうしの関係
   - 職種・役割の定義と、似た役割との違い・関係（何を決める役割か、誰に何を渡すか）
   - 会議体、承認の流れなどの決めごと
   - 人は役職・役割名で書き、個人名は書かない。「誰がどこに所属するか」「誰が長か」は拾わない

## 入れないもの

- 1つのリポジトリの中で完結する実装の詳細。関数の挙動、設定値、CIやブランチの運用など（そのリポジトリのdocs向き）
- AIの作業手順や好みへの指示（memory向き）
- その日だけの作業状況。PRの状態、デバッグの途中経過など（日報向き）
- 人事・評価・候補者についての情報。個人の所属・異動・役職への就任も含む
- 一般的な技術知識

## 種別と本文の形

| kind     | 本文の形                                                                                                        | dest_hint                                                                             |
| -------- | --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| `term`   | `- 意味:`（1〜2文） `- 別名:` `- 起点:` の箇条書き。分からない項目は書かない                                    | `glossary`                                                                            |
| `system` | 1行目に「この知識が答える問い」。本文を続ける。構成やシーケンスはMermaidで書く                                  | cross-repoは `06_Domain/<主題>/`、projectは `06_Domain/<project>/`                    |
| `org`    | 組織構造は、組織単位・職種ごとの担当範囲と関係。会議体は、参加者、決めること、情報の流れ。図はMermaid flowchart | 組織単位・職種は `05_Organization/組織構成.md`、会議体・決めごとは `05_Organization/` |
| `skill`  | 繰り返された依頼の文面と回数                                                                                    | なし                                                                                  |

## 出力

次のJSONだけを返す。前後に文章を付けない。
渡されたdigestごとに `results` へ1要素を入れる。
`session_id` はdigest冒頭の見出し（`# <source> session <id>`）の id を使う。
候補が無いdigestも、`candidates` を空配列にして入れる。
`confidence` は `high` か `low` のどちらかにする。`medium` などほかの値は使わない。

```json
{
  "results": [
    {
      "session_id": "<digestのsession id>",
      "candidates": [
        {
          "kind": "term | system | org | skill",
          "scope": "cross-repo | project（systemのときだけ）",
          "title": "短い見出し",
          "body": "上の表の形の本文",
          "evidence": ["根拠になった発言の短い引用"],
          "dest_hint": "06_Domain/example-project/",
          "confidence": "high | low"
        }
      ]
    }
  ]
}
```
