# esa 週次エグゼクティブレポート生成

複数のesa記事の直近一週間の差分を収集し、部長会向けエグゼクティブレポートを生成する。

追加の記事指定（任意）: $ARGUMENTS
形式: `<team> <post_number> [<team> <post_number> ...]`

## 参照スキル

- `.config/claude/skills/esa-api/SKILL.md` — esa API アクセス方法

## 手順

### 1. 対象記事リストの構築

1. `.config/claude/skills/esa-weekly-report/esa-weekly-report-posts.json` から固定リストを読み込む
2. `$ARGUMENTS` に追加の `<team> <post_number>` ペアがあればリストに追加

### 2. 各記事の差分収集

対象記事ごとに以下を実行する。各記事は独立しているため並列Bash呼び出しで処理すること。

**差分の集計期間は「定例と定例の間」とする。** 定例は毎週金曜 15:00 に開催され、その場で表示される内容は「金曜 15:00 直前時点のリビジョン」である。したがって収集したいのは `前回の金曜 15:00 定例時点 → 今回の金曜 15:00 定例時点` の差分。

1. `esa-api` スキルに従い、リビジョン一覧を取得
2. 前回定例の日時を特定: 今回の定例（直近の金曜 15:00）の1つ前の金曜 15:00（= 前回SoSで参照された時点）
   - 例: 今回の定例が 07-17(金) なら、前回定例は 07-10(金) 15:00
3. FROM を決定: **前回の金曜 15:00 より前（strictly before）に作成された最新リビジョン**（= 前回定例で表示されていた内容）
   - `created_at < 前回金曜 15:00` を満たすリビジョンのうち最新のもの
   - 注意: 金曜 15:00 **以降**（定例中〜定例後）に編集されたリビジョンは前回定例には表示されていないため、今回の差分に含める。この判定を誤ると FROM が1つ後ろにずれる（例: 金15:27 のリビジョンを選ぶと誤り、正しくはその手前の 金14:59 のリビジョン）
4. レポートに載せる compare URL を生成: `https://<team>.esa.io/posts/<number>/revisions/compare/<from>...head/html_diff`
   - ブラウザURLは TO を `head` とする。SoS直前に記事が追記更新された場合でもURLを書き換えずに最新差分を表示できる
5. compare API で diff 内容を取得
   - API は `head` キーワード非対応（404）。API呼び出しでは具体的なリビジョン番号（現時点の最新番号を TO）を指定する
   - diff は `diff_text` フィールド（`.diff_text // .diff.diff_text`）が読みやすい。`+`/`-` 行を抽出して使う

**差分が無い場合:**
- 前回金曜 15:00 以降にリビジョンが増えていない → 「変更なし」と記録し、レポートでは省略

### 3. エグゼクティブレポート生成

収集した全記事の差分を統合し、以下の構造でレポートを作成する:

```markdown
# 週次レポート（YYYY-MM-DD）

## サマリ
- 【検索】変更概要（1行）
- 【素材登録】変更概要（1行）
- 【サブシステム名】変更概要（1行）
- 【予約】変更概要（1行）
- 【基盤 / システム名】変更概要（1行）
- ...
※ サブシステム名は記事の label を使用
※ 基盤のみ、記事内のシステム名（航空キュー基盤、料金計算基盤 等）の粒度で分けて記載
※ リスクや特に注意が必要な事項があれば ⚠ を付けて明示

## 記事別の変更点

### [label]
- compare URL: <url>
- 主な変更点
  - ...

### [label]
...
```

レポートのルール:
- 記事別の変更点: diff から読み取れる事実のみ記載
- サマリ: 事実に基づく仮説や示唆を含めてよいが、仮説部分は「（仮説）」と明示する
- 技術的詳細は最小限に抑える
- 出力後にユーザーがレビューするため、仮説の正誤はユーザー判断に委ねる

### 4. 部長会報告用メモ生成

**同一ファイル内**に、`---` 区切りで続けて出力する。手順3のレポートが「記事ごとに何が変わったか」を記録するのに対し、こちらは**部長会でそのまま読み上げるための資料**であり、軸が異なる:

- 手順3 = 記事（サブシステム）軸
- 手順4 = 案件軸（サマリ）＋サブシステム軸（各セクション）

```markdown
---

# 部長会報告用メモ

## サマリ

- 全体を1〜2文で総括（今週何が前進し、何が新たなリスクになったか）

- 【案件】
  - 🔴 案件名（サブ名）: 先週からの変化 → だから何（要判断 / リスク / 見通し）
  - 🔴 ...
- 【障害・臨時リリース】
  - 🔴 サブシステム名 {発生日} {概要} {影響顧客}: 原因・対処・残タスク

## 検索 🌫️

- 🔴 案件名: 変更内容
- 🟢 案件名: 変更内容
- 障害
  - 🔴 {発生日} {概要} {影響顧客}: 原因・対処・残タスク
  - 🟢 ...

## 素材登録 🌫️

## サブシステムB ☔

## 予約 ☔

## その他基盤 ☀️

- 🟢 直近一週間の更新なし（変更なし）

凡例

```
- 🔴: 更新箇所・重要な箇所
- 🟢: 更新はあるが部長会で読み上げるほどではない箇所
```

```
- ☀️：現時点で問題なし
- 🌫️：現時点では問題ないが不確実性が高い
- ☔：現時点で問題が顕在化している
```
```

部長会報告用メモのルール:

**サマリは「全体報告で口頭で読み上げる分量」に収める。** サブシステム別セクションの再掲になった時点で冗長。役割を分ける:
- サマリ = **なぜ報告するか**（判断が要る / リスク / 約束が変わった）
- サブシステム別セクション = **何が変わったか**（詳細はこちらに委ねる）

- **載せる基準**: 以下のいずれかに該当する案件だけをサマリに載せる。該当しなければ載せない（下のセクションで拾えるため）
  1. 判断・支援を仰ぎたい（エスカレーション）
  2. 顧客との約束が変わった（納期・リリース日・スコープ）
  3. リスクが顕在化した、または解消した
  4. 新規障害・臨時リリース
- **🟢はサマリに載せない**。🟢は「部長会で読み上げるほどではない」と定義しているため、サマリに置くと定義矛盾になる
- **上限は案件5件**。超える場合は基準1→4の優先順で落とす
- **1案件1行**。サブシステム別の内訳を入れ子にしない。複数サブに跨る案件は `案件名（サブA・サブB）` とサブ名を併記し、状況は横断で1文にまとめる
- **各行は「変化 → だから何」で書く**。「〜を開発中」「〜を対応中」といった定常進捗は変化ではないので載せない
- **【案件】は案件軸で束ねる**。同一案件が複数サブシステムに跨る場合、サブごとに分けず案件1行にまとめる。部長会では「案件がどう進んでいるか」が問われるため
- **🔴/🟢 の判定**: 🔴 = 部長会で読み上げる（新規障害、スケジュール・体制の変更、リスクの顕在化・解消、重要マイルストーン到達）。🟢 = 変更はあるが読み上げ不要（定常的な進捗、細かい仕様調整）
- **サブシステム見出しの天気アイコン**は、**そのサブシステムの稼働の大半を占める主要案件の状態**で決める。記事内の☔案件を単純に伝播させない（大型案件を常に抱えるサブは☔に張り付き、情報量がゼロになるため）
  - 判定手順:
    1. 記事内の案件のうち、担当人数・記述量・納期の近さから**主要案件を1〜2件特定する**
    2. その主要案件の状況マーク（☀️/🌫️/☔）と本文の記述を見て、サブシステムのマークを決める
    3. 主要案件でない案件が☔でも、稼働比率が小さい、または現場が「リカバリ不要」と判断していれば引き上げない
  - 前週の `05_Organization/Buchokai/` のファイルで同じサブシステムに付けたマークを必ず確認し、**変えるなら理由を1行で書ける状態にする**。前週と同じなら据え置く
  - 差分がなかった記事は前週のマークを踏襲する
  - よくある誤り: 主要案件が改善しているのに、残った小さな☔案件を拾ってサブ全体を☔に落とす。改善した週に悪化表示することになるので避ける
- **並び順**: サブシステム各セクション内は以下の順に並べる
  1. 第一ソートキー = **種別**（案件 → 障害）。案件はセクション直下にフラットに並べ、障害は `- 障害` の下に入れ子で並べる
  2. 第二ソートキー = **🔴 → 🟢**
  3. 障害が同色で並ぶ場合は 新規 → 既報、さらに同条件なら発生日の新しい順
  - 障害がない週も `- 障害` / `- 🟢 なし` と記載する（読み上げ時に触れるため省略しない）
  - サマリの【案件】【障害・臨時リリース】も同じく 🔴 → 🟢 の順に並べる
  - ベロシティは部長会報告用メモには載せない（手順3のレポート側にのみ記載する）
- **障害の記法**は次に統一する:
  - サブシステム各セクション: `{発生日} {概要} {影響顧客}: {状況}`
    - 例: `🔴 6/25 列車変更に失敗した際に利用可能な予約が消失 CUST-A: 誤ったロールバック処理が原因。7/17の臨時リリースで削除済、類似事象を調査中`
  - サマリの【障害・臨時リリース】: 横断で読むため先頭にサブシステム名を付ける → `{サブシステム} {発生日} {概要} {影響顧客}: {状況}`
  - 発生日は記事の「発生時期」を採用する（対処日・リリース日ではない）。年は省略し `M/D` 形式
  - 影響顧客は顧客略号（3文字程度の略号。実際の対応は `~/.claude/local-context.md` を参照）。サブシステム名やサイト名は概要側に含める
  - 状況には原因・対処・残タスク（ポストモーテム未作成、調査中 等）を含める
- 各行は1行で完結させる。読み上げ資料なので改行や入れ子を増やさない
- 差分がなかった記事も「直近一週間の更新なし」として省略せず記載する（手順3では省略してよいが、こちらは読み上げ時に触れるため）
- 手順3と同様、事実は diff 由来のものに限る。ただし前週レポート（`05_Organization/Buchokai/` の直近ファイル）を参照して「先週◯◯だった状態から前進」のような週跨ぎの文脈を補ってよい

### 5. 出力

1. **ファイル保存**: `~/Obsidian/05_Organization/Buchokai/YYYY-MM-DD.md` に保存
   - 手順3のエグゼクティブレポートと手順4の部長会報告用メモを、`---` 区切りで**1ファイルにまとめて**保存する（ファイルを分けない）
   - ファイル名の日付は今日の日付
   - 既存ファイルがある場合はユーザーに確認
2. **会話内表示**: レポートのサマリを会話内にも表示
