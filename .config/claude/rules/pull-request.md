# PR作成方針（GitHub）

大きな変更は stacked PR で分割し、各PRをレビュー可能なサイズに保つ。

## 原則

- **粒度の基準はレビュアーの負荷**。「1回のレビューで読み切れる量」を1PRとする。
- PRは**レビュー観点がまとまった単位**で、関連する複数コミットの束にする。1コミット＝1PRにはしない。
  - 「コミットの分割」ルール（1コミット＝1つの論理的変更）の一段上のレイヤーとして、コミットをレビュー観点で束ねたものがPR、と位置づける。
- スタック内の各PRは**単体でビルド・テストが通り、そのPRまでマージしても壊れない**状態にする。
- PRの目的が**1文で説明できる**こと。説明に「〜と〜」が必要になったら分割を検討する。

## サイズの目安

- 変更**±400行程度**を超えそうならスタック分割を検討する。
- 硬い上限ではなく**分割を検討するトリガー**として使う。分割するとかえって読みにくくなる場合は無理に切らない。
- lockファイル等の自動生成分は行数に数えない。

## 切れ目の例

レビュー観点が変わるところで切る。

- 準備リファクタ → 本体実装 → 後片付け
- 型・スキーマ定義 → 実装 → 呼び出し側の移行
- 機械的な一括変更（リネーム・フォーマット）→ ロジック変更

## 例外

- 目安以下に収まる変更は**単発PRでよい**。スタックを強制しない。
- チーム・リポジトリ側に別のPR規約がある場合はそちらを優先する。

## ツール

- スタックの作成・push・rebase・マージ後の同期は `gh-stack`（gh CLI拡張）を使う。
