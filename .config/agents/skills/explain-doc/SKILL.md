# explain-doc

読み手に前提知識が無くても伝わる説明文書を書く。
「何を定義し、何を図にするか」を決めるskillで、文体は tech-writing に従う。

## 1. 読み手を決める

読み手を次のどれかに決める。依頼から読み取れなければ1回だけ聞く。

- **社内エンジニア**：用語表で定義した略語・コード名を使ってよい
- **社内の非エンジニア**：業務の言葉で書く。システム名は役割を添えて出す
- **顧客・他社**：社内略語・コード名・repo名を出さない

語の平易さの基準はここで決まる。詳細は `references/terms.md`。

## 2. 用語表を先に作る

本文で使う固有語・略語・登場人物（人・システム・組織）を、冒頭に並べる。

```markdown
## 用語

- **予約管理システム**：宿の予約を受け付けて在庫を減らすシステム
- **担当者**：予約の変更を承認する宿側の人
```

- 以後、本文・図・見出しはこの表の語だけを使う。同じものに別名を付けない
- 社内固有語の意味が分からなければ glossary skill を引く。推測で埋めない

## 3. 図を選ぶ

3つ以上の要素の関係・手順・構成は、文章だけで説明しない。依頼されなくても図を描く。
図の種類と形式は `references/diagrams.md` の選択表で決める。

## 4. 出す前の自己チェック

出す前に下表を順に確認し、違反を直してから出す。

| ID  | 確認すること                                                                       |
| --- | ---------------------------------------------------------------------------------- |
| T1  | 用語表に無い固有語が、本文・図・見出しに出ていない                                 |
| T2  | `references/terms.md` の抽象語を、中身を言わずに使っていない                       |
| T3  | 読み手が顧客のとき、社内略語・コード名・repo名が残っていない                       |
| D1  | 図のノード名・ラベルが用語表と一字一句一致している                                 |
| D2  | 本文から図の要素を指すときに①②③の番号で対応している                                |
| D3  | 検証していない推測の要素を図に入れていない。入れる場合は破線か「(要確認)」を付ける |
| D4  | 1図1主張になっている。要素が多ければ図を分ける                                     |

## 規範を育てる

同じ修正指示を2回受けたら、`references/` の該当ファイルへ追記する。
public repositoryなので、例は架空・汎用の語で書く。
