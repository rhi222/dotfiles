# PRのタイトルと本文

`wt-pr` / `backport-pr` の両方から参照する。

## 材料の集め方

```bash
BASE=<ベースブランチ>
git log --oneline "$BASE"..HEAD      # 積んだコミット
git diff --stat "$BASE"..HEAD        # 変更ファイルと規模
```

コミット履歴が意図の単位で割れていれば、そのままPR本文の骨格になる。

## タイトル

コミットと同じ Conventional Commit 形式で、**PR全体を1文で言い切る**。

```
fix(mail-list): 一覧画面のハイドレーションエラーを修正する
chore(knip): 未使用export/型/enumメンバー30件を削除 (PROJ-124)
```

チケット番号があれば末尾に括弧で添える。タイトルに「〜と〜」が必要になったら、
それはPRを分けるサイン（後述）。

## 本文

```markdown
## 背景

なぜこの変更が要るか。事象・チケット・元スレへのリンク。
読み手が「直す価値があるか」を判断できる材料を置く。

## 変更内容

- コミット単位、または関心事単位で箇条書き
- 何をどう変えたかを、diffを開かなくても追える粒度で

## 確認方法

レビュアーが手元で確かめる手順。自動テストで担保できている場合はその旨。

## 補足

判断に迷った点、意図的に対象外にしたこと、後続で対応する予定のもの。
無ければ節ごと省く。
```

**節を埋めるために書かない。** 背景が自明なら1行でよいし、補足が無ければ消す。
空の節が並ぶとレビュアーが読み飛ばす癖をつけてしまう。

Claude Codeの署名は含めない。

## サイズと分割

粒度の基準は**レビュアーの負荷**。「1回のレビューで読み切れる量」を1PRとする。

- 変更 **±400行程度**を超えそうならスタック分割を検討する（硬い上限ではなくトリガー）
- lockファイル等の自動生成分は行数に数えない
- PRの目的が1文で説明できること。説明に「〜と〜」が要るなら分割を検討

切れ目はレビュー観点が変わるところに置く。

- 準備リファクタ → 本体実装 → 後片付け
- 型・スキーマ定義 → 実装 → 呼び出し側の移行
- 機械的な一括変更（リネーム・フォーマット）→ ロジック変更

分割するとかえって読みにくい場合は無理に切らない。目安以下に収まる変更は単発PRでよい。
スタックが必要になったら `gh-stack`（gh CLI拡張）を使う。

## 作成コマンド

```bash
gh pr create --base "$BASE" --title "<title>" --body "<body>"
```

`--base` は必ず明示する。省略するとデフォルトブランチに向くため、
案件別の長命ブランチを持つリポジトリでは作り直しになる。
リポジトリごとの対応は `~/.claude/local-context.md` を見る（dotfilesは public なので値は書かない）。

draftで出したいときは `--draft` を足す。実装が途中で、先にCIだけ回したい場合に使う。
