# コミットの分割とprefix

`wt-pr` / `backport-pr` の両方から参照する。

## なぜ分けるか

あとから `git log` や `git blame` を見た人が、**なぜこの変更をしたかを1コミットで理解できる**状態にするため。
副次的に `git bisect` が壊れなくなる。

## 分割の判断基準

次に当てはまったら分割を検討する。

- コミットメッセージに「〜と〜」「ついでに」「あわせて」を書きたくなった
- 1つのtype（`feat` など）に複数の独立した関心事が入っている
- 複数ファイルの変更だが、目的が別々

**リファクタリングと機能追加・修正は必ず分ける。** 「動作を変えない整理」と「動作を変える実装」を
混ぜると、レビュアーがどの差分を疑えばよいか判断できなくなる。

フォーマット・リネームのみの機械的変更も単独コミットにする。差分レビューのノイズになるため。

逆に、**片方だけコミットすると壊れる変更**（実装とその型定義など）は無理に分けない。
各コミットはそれ単体でビルド・テストが通る状態を保つ。

## 分けるための操作

```bash
git add -p              # ハンク単位でステージ
git add <path>          # ファイル単位でステージ
git diff --staged       # ステージ内容が単一の意図に閉じているか確認
```

## prefix

| prefix     | 使う場面                                   |
| ---------- | ------------------------------------------ |
| `feat`     | 新機能の追加                               |
| `fix`      | バグ修正                                   |
| `refactor` | バグ修正でも機能追加でもないコードの変更   |
| `perf`     | パフォーマンス改善                         |
| `test`     | テストの追加・修正                         |
| `docs`     | ドキュメントのみの変更                     |
| `style`    | 動作に影響しない変更（空白・フォーマット） |
| `chore`    | 補助ツール・ライブラリ更新など             |
| `ci`       | CI設定・スクリプトの変更                   |
| `build`    | ビルドシステム・外部依存への影響           |

迷ったときの分岐は `.config/claude/skills/git-commit/SKILL.md` にフローチャートがある。

## 書き方

- 本文は日本語で簡潔に
- scopeは変更範囲が明確なときだけ付ける（`fix(payment):` など）
- Claude Codeの署名（`🤖 Generated with` / `Co-Authored-By: Claude`）は**含めない**
  （`settings.json` で `includeCoAuthoredBy: false` にしているため、手動作成時も揃える）

```
feat(booking): 企画箇所の会員資格フラグを新規予約APIへ渡す

TACOの箇所情報取得APIが返す2フラグを予約記録経由で受け取り、
画面表示の出し分けに使えるようにする。
```
