# Business Modeling

社内外の関係者が、業務の目的・境界・用語・ルール・具体例を同じ意味で話せるモデルを作る。
図の完成ではなく、図を使って認識差と未決事項を発見することを成果とする。

## 進め方

1. 依頼、議事録、仕様、コードなどから、今回揃えたい認識と対象範囲を一文で示す。
2. 確認できた事実、推測、資料間の不一致、未確認事項を混ぜずに抽出する。
3. 次の表から、問いに答える最小限のモデルを選ぶ。指定がなければ図を増やさない。
4. Mermaid図と、その図から判明した認識差・未決事項を提示する。
5. 更新対象の文書がある場合は、既存の表記と図を保ちながら差分を反映する。

| 揃えたい認識                 | モデル                      | Mermaid                   |
| ---------------------------- | --------------------------- | ------------------------- |
| 開発対象と社内外の境界       | システム関連図（SUDOのS）   | `flowchart`               |
| 利用者が達成すること         | ユースケース図（SUDOのU）   | `flowchart`               |
| 業務概念・関係・ルール       | ドメインモデル図（SUDOのD） | `classDiagram`            |
| 抽象モデルが実例で成立するか | オブジェクト図（SUDOのO）   | `flowchart`               |
| 部門間の作業と受け渡し       | 業務フロー                  | `flowchart` と `subgraph` |
| やり取りの時系列             | シーケンス図                | `sequenceDiagram`         |
| 状態と遷移条件               | 状態遷移図                  | `stateDiagram-v2`         |
| 永続化するデータの構造       | ER図                        | `erDiagram`               |
| 複数条件による判断           | デシジョンテーブル          | Markdown表                |

SUDOモデリング、ドメインモデル、オブジェクト図を作る場合は
[references/modeling-guide.md](references/modeling-guide.md)を読む。

## モデリングの原則

- 図の冒頭に「この図で答える問い」を一文で置く。
- 現在の業務（AS-IS）と変更後（TO-BE）を同じ図に混ぜない。
- 業務用語は関係者が使う名前を採用し、同義語や解釈差は用語表へ残す。
- 業務モデルへ技術都合のクラス、テーブル、APIを持ち込まない。
- システム化の前に、工程を削除・統合・単純化できないか確認する。
- 正常系だけでなく、取消、差戻し、期限切れ、重複、変更を扱う。
- 根拠のない関係、多重度、ルールは断定せず `仮説` と明記する。
- 図で表しにくい条件、根拠、判断者はMarkdown表で補う。
- Mermaidが直接対応しないUML表現は`flowchart`で簡潔に代替し、見た目の再現にコードを費やさない。

## 出力

必要な項目だけを出す。

```markdown
## この図で答える問い

## モデル

（Mermaid）

## 用語・業務ルール

## 認識差・未決事項

| 論点 | 現在の理解 | 根拠 | 確認先 |
| ---- | ---------- | ---- | ------ |
```

資料やコードが根拠の場合は、可能な限りファイル名と行番号を付ける。
情報不足でも作れる暫定モデルは作り、不明点だけを明示する。モデル全体を想像で補完しない。
