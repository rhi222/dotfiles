# PR説明文を整理する

事実を保ったまま、レビュアーが「なぜ・何が・どう確認されたか」を上から順に読める本文へ再構成する。

## 1. 入力と操作範囲を確定する

- ユーザーが本文を提示した場合は、その文章を主な入力にする。
- PR番号、URL、または現在のブランチが対象なら、利用可能な `gh` と `git` で既存本文、PRテンプレート、コミット、ベースとの差分を確認する。
- リポジトリにPRテンプレートがある場合は、必須見出し、チェックボックス、HTMLコメントを保つ。
- 本文案の提示を既定とする。PRの作成、タイトル変更、本文更新などのリモート操作は、ユーザーが明示的に依頼した場合だけ行う。
- 本文の整理だけで十分なら、不足情報を埋めるための質問で作業を止めない。意味が大きく変わる不明点だけを質問する。

## 2. 根拠を集める

次の順に、依頼に関係する範囲だけ確認する。

1. ユーザーが示した目的、制約、既存本文
2. PRテンプレートと既存PRのメタデータ
3. ベースブランチとの差分とコミット履歴
4. テスト結果、関連Issue、運用・移行上の注意

コミットメッセージだけで意図を決めず、可能なら差分で裏付ける。差分から分からない動機、効果、互換性、テスト結果を推測しない。「影響なし」「すべて確認済み」などの強い表現は根拠がある場合だけ使う。

## 3. 読み手の順序で組み立てる

リポジトリ固有のテンプレートがなければ、次を基本形にする。

```markdown
## 概要

[解決する問題と、このPRでどう変わるか]

## 変更内容

- [利用者やシステムから見た変更]
- [実装上の重要な変更]

## 確認方法

- [実行したテストや確認結果]
```

必要な場合だけ、`レビューポイント`、`影響範囲`、`設計上の判断`、`移行・リリース時の注意`、`関連Issue` を追加する。情報がない見出しを「なし」で埋めない。

- 概要では背景を長く語る前に、問題と結果を2〜4文で示す。
- 変更内容はファイル一覧やコミット順ではなく、挙動・責務・関心事でまとめる。
- 詳細はレビュー判断に必要なものへ絞り、実装を読めば分かる逐語的な説明を省く。
- 特に見てほしい判断、既知の制約、意図的に対象外にした事項があれば明示する。
- テストは実行したコマンドと結果を区別する。未実行なら未実行と書き、成功した体裁にしない。
- Issueを自動で閉じる語句やリンクは、入力に存在するか関係が確認できた場合だけ残す・追加する。

## 4. 文章を磨く

- 元の言語とプロジェクトの文体を基本的に維持する。
- タイトルの言い換えだけの冒頭、同じ内容の重複、変更ファイルの羅列、コミットログの転記を削る。
- 抽象語より、対象と変化が分かる具体的な名詞・動詞を使う。
- 一文を短めにし、箇条書きは並列な内容にだけ使う。
- 太字、絵文字、注意書き、深い見出しを増やしすぎない。
- コード、設定名、識別子、コマンド、チェックボックスは意味が変わらないよう正確に保つ。
- 元本文にない成果や価値を宣伝調で足さない。

## 5. 出力する

- 最初に、そのまま貼り付けられるMarkdown本文案を出す。
- 重大ではない不足情報がある場合は、本文の後に「補足が必要な点」として本文外へ簡潔に示す。
- 変更理由の長い解説や修正箇所一覧は、ユーザーが求めた場合だけ付ける。
- PR本文を更新した場合は、更新したPRと変更の要約を報告する。
