# Markdown文書を整理する

既存文書が持つ事実、判断、理由、条件、例外、手順、参照先を保ち、読者が前から順に理解できる形へ再構成する。

## 1. 編集条件を確認する

- 対象ファイル、想定読者、文書の目的、既存の文書規約を確認する。リポジトリ内の文書なら、関連する `AGENTS.md`、文書索引、リンク検査も確認する。
- ユーザーが構成案だけを求めた場合は原文を変更しない。ファイルの整理を依頼された場合は対象を直接編集する。
- 文書の意味を変える不明点だけを質問する。構成上の判断は原文から推定して進める。

## 2. 固有情報を棚卸しする

編集前に、次の情報を意味単位で把握する。

- 事実、結論、主張とその根拠
- 前提、対象範囲、制約、例外、未確定事項
- 手順、入出力、状態遷移、依存関係、時系列
- コマンド、コード、設定値、数値、固有名、リンク、注記
- 用語と、その定義または文脈上の意味

同じ意味の反復は一つに統合してよい。ただし、似ているだけの別条件、別理由、別事例を重複とみなさない。情報が衝突している場合は勝手に一方へ統一せず、矛盾または確認事項として残す。

## 3. 読む順序へ組み替える

見出しや段落を、執筆された順ではなく理解に必要な順へ並べる。通常は「目的と対象範囲 → 前提と用語 → 全体像 → 詳細 → 手順 → 例外と注意 → 参照」の流れを候補にするが、文書の役割に合わなければ強制しない。

- 一つの節には一つの論点を置く。別の論点が混ざる節は分け、同じ役割の節は統合する。
- 見出しだけで内容と階層が分かるようにする。`背景`、`詳細`、`その他` のような曖昧な見出しは具体化する。
- 参照される概念や用語は、原則として利用箇所より前で定義する。既存の定義がない用語は、文脈から確定できる範囲だけ明文化する。
- 見出しの項番は、長い仕様書や設計書など参照番号が役立つ場合に採番する。番号は階層と一致させ、単一ページの短い文書には機械的に付けない。
- 箇条書きは並列事項、番号付きリストは順序や参照番号に意味がある事項へ使う。
- 既存リンク、見出しアンカー、目次、相互参照は構成変更に合わせて更新する。外部から参照される可能性があるアンカーは、互換性を確認せず壊さない。

## 4. 図が理解を助ける場合だけ図示する

三つ以上の要素の関係、分岐を含む処理、状態遷移、時系列、階層が文章だけでは追いにくい場合はMermaidを使う。

- フローは `flowchart`、時系列は `sequenceDiagram`、状態は `stateDiagram-v2`、構造は `classDiagram` または `erDiagram` を候補にする。
- 図は原文から確認できる関係だけを表し、新しい仕様や因果を足さない。
- 図の直前に何を読む図かを一文で示す。正確な条件、値、例外は本文にも残し、図だけを唯一の情報源にしない。
- 本文をそのまま箱へ移しただけの図や、二要素だけの自明な関係図は作らない。
- ノードIDと表示名を分け、記号を含む表示名は引用符で囲み、Mermaidとして解釈可能な構文にする。

## 5. 情報を保ったことを確認する

編集後に原文と見比べ、棚卸しした固有情報が次のいずれかに存在することを確認する。

1. 本文に残っている
2. 同義の記述へ統合されている
3. 表、箇条書き、注記など別の表現へ移されている

特に否定、例外、条件、不確実性、数値、コマンド、リンクが消えていないか確認する。読みやすさだけを理由に、背景、判断理由、失敗例、運用上の注意を大幅に要約しない。

リポジトリ内のファイルを編集した場合は、既存のMarkdown lint、リンク検査、文書固有の検証を実行する。検証手段がなければ、見出し階層、リンク、コードフェンス、Mermaid構文を目視で確認する。

## 6. 結果を返す

- 編集を依頼された場合は整理後の文書を完成させ、主な構成変更と検証結果だけを報告する。
- 構成案を依頼された場合は、提案する目次と、各節へ移す原文の情報を対応づける。
- 原文の矛盾、意味を確定できない用語、欠落している参照先は、本文と混同せず確認事項として示す。
