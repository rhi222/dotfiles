# テストの設計規範

`tests/<domain>/test-*.sh` と Go unit test を書く・直すときの規範。
置き場と実行の仕組みは [scripts-layout.md](scripts-layout.md)、
検証コマンドは [../AGENTS.md](../AGENTS.md) を見る。

## 何をテストするか

- **壊れたら実害がある不変条件**をテストする。テストファイル冒頭のコメントに
  その不変条件を1〜3行で書く（既存テストの慣行を必須化する）
- **事故起点の回帰テストは出自を書く。**「今回の障害を検知するための回帰」のように
  自己申告する既存の慣行を続ける。出自が書いてあれば、後で仕様が変わったときに
  消してよいかを判断できる
- 仕様網羅は**分岐・境界・終了コード・副作用・失敗時状態**の軸で押さえる。特に
  cleanup、adopt、同期処理は、dry-run が無変更であること、失敗時に既存状態を
  壊さないこと、再実行や競合を安全に扱えることを検査する
- 同じ同値クラスの入力で同じ分岐を繰り返さない。ただし空白・改行・glob 文字、
  壊れた JSON など、解釈や境界条件が異なる入力は別ケースとして扱う

## 何を固定してよいか

| 対象 | 固定 | 理由 |
| ---- | ---- | ---- |
| 終了コード・ファイルの有無・呼び出し引数 | する | 呼び出し側との契約そのもの |
| 機械可読な契約行（`<script名>: KEY=VALUE`） | する | 表示を変えても壊れない検査点として設ける |
| 人間向け文言の完全一致・絵文字・全角スペース | しない | 文言調整のたびにテストが落ちる |
| 文字列整形関数の出力 | する | 整形そのものが仕様（herdr の `format_duration` など） |
| 外部コマンドのサブコマンド文字列 | 最小限 | gh 等の引数構成に密結合しない。動作の結果で判定できるならそちら |

- 人間向けメッセージは完全一致を避ける。通知の有無や件数に加え、対象名・操作・
  危険性など、利用者の判断に必要な意味要素だけを部分一致で固定する
- 実際の呼び出し側が機械的に値を読む必要があるなら、人間向け表示と分離した契約行を
  設ける。テストだけを理由に本番の出力契約を増やさない。出力先は呼び出し側との契約に
  合わせ、成功時の stderr 追加が cron・ログ・`2>&1` の利用者へ影響しないことを確認する
- 契約行を設ける場合の書式は `<script名>: KEY=VALUE [KEY=VALUE...]` とする
  （先例: `env-residue: FOUND=N`。キーが複数なら `<script名>: CONTEXT=cron HITS=missing`
  のように並べる）
- テスト内リテラルの二重管理（fixture と assert で同じ ID を別々に書く）は変数で
  単一ソース化する

## 時間に依存しない

- **経過時間の閾値アサーションを書かない**（`elapsed -lt 4` の類）。並列性は
  バリア（全 worker が互いのマーカーを待つ）で、直列性はオーバーラップ検出
  （実行中マーカーの同時存在）で証明する
- background 処理の完了待ちは固定 `sleep` でなく**上限付きポーリング**にする
- タイムアウトの検査だけは大きな上限（実値の10倍程度）なら許す
- `# serial: <理由>` は最後の手段。時間依存を除去してから、それでも不安定な
  ものだけに付ける

## 反復パターン

- 「ツール導入済み→呼ぶ / 未導入→skip して rc=0 / ツール失敗→rc 伝播」のような
  定型3分岐が3回以上並んだら、そのテストファイル内でヘルパ関数に畳む
- ファイルを跨ぐ harness 共通化はしない（[scripts-layout.md](scripts-layout.md) の判断）
